## 1. 문서의 기준과 결정 범위

### 1.1 세 종류의 내용을 구별한다

프로토타입이 실행된다는 이유만으로 본편의 난이도와 플레이 시간이 검증되었다고 판단하지 않는다.

### 1.3 이번 기초 개발의 완료 경계

포함하는 것은 실제 플레이에 필요한 가장 작은 연결 흐름이다.

1. JSON에서 방을 읽고 잘못된 데이터에 원인을 표시한다.
2. 한 화면에 보드, 목표, 운반물, 조작법, 행동 결과를 보여준다.
3. 이동·줍기·내려놓기·설치·조립·배치·가동을 실행한다.
4. 각 방에서 복구를 완료하고 빈손으로 출구에 도착한다.
5. 행동을 되돌리거나 방을 재시작하고, 완료 후 다음 방으로 이동한다.
6. 현재 여섯 방의 해결 행동열과 주요 경계 조건을 자동 검사한다.

본편 8개 완성, 최종 아트·음원, 저장·불러오기, 점수, 시간 제한은 이번 완료 조건에 넣지 않는다. 발판·연결문, 뼈 투입구, 벨트를 4~6번 응용방 프로토타입에 적용한다. 7·8번 방과 최종 난이도·분량 검증은 후속 작업으로 남긴다.
기초 방은 조작과 규칙의 검증용이며, 최종 입문방의 분량과 연출을 확정하지 않는다.

## 2. 플레이 경험과 퍼즐 설계 원칙

### 2.1 플레이어가 반복해서 하는 판단

| 시점 | 판단 | 화면이 제공해야 하는 정보 |
| --- | --- | --- |
| 시작 | 어느 복구 대상부터 처리할지 | 부품·뼈·작업대·초소·레버·출구의 위치 |
| 운반 | 하나뿐인 손을 무엇에 사용할지 | 운반물 이름과 현재 칸에서 가능한 행동 |
| 설치 | 통로를 계속 사용할 수 있는지 | 설치 완료와 가동 상태의 명확한 구별 |
| 배치 | 초소를 막아도 남은 재료에 접근 가능한지 | 배치 후 통행 불가 안내 |
| 가동 | 출구 쪽에 필요한 작업이 모두 끝났는지 | 남은 복구 수와 가동될 함정 위치 |
| 막힘 | 직전 행동을 고칠지 처음부터 다시 할지 | 되돌리기와 재시작 키, 현재 행동 수 |

복잡한 조작보다 순서 선택에 사고를 쓰게 한다. 이동 속도나 반응 속도로 퍼즐을 어렵게 만들지 않는다.
정답 순서를 외우게 하기보다, 특정 순서를 선택해야 하는 공간상의 이유를 보이게 한다. 실패 행동은 즉시 이유를 알리고 자원을 소비하지 않는다.
막힌 순서는 되돌리기로 복구할 수 있어야 한다.

### 2.2 레벨을 채택하는 조건

- 최소 한 개의 해결 행동열을 실제 규칙 엔진에서 재생할 수 있다.
- 핵심 장치가 없어도 풀리는 방이라면 그 장치가 필요한 이유를 다시 검토한다.
- 중요한 길막힘은 장치의 배치와 상태에서 예측할 수 있다.
- 새 규칙은 먼저 안전한 장소에서 배우고, 다음 방에서 기존 규칙과 결합한다.
- 운반 거리만 늘려 분량을 채우지 않는다.
- 정답 외의 순서도 규칙상 유효하면 허용한다. 특정 행동열만 정답으로 검사하지 않는다.
- 자동 해결 검사는 가능성만 증명한다. 재미와 난이도는 사람의 플레이로 확인한다.

## 3. 보드와 점유 규칙

### 3.1 좌표와 시간

프로토타입 결정: 논리 보드는 정수 좌표 `(x, y)`를 사용한다. 왼쪽 위가 `(0, 0)`이고, 오른쪽으로 `x`, 아래쪽으로 `y`가 증가한다.
방향 입력 한 번은 논리 보드의 한 칸 이동이다. 대각선 이동과 실시간 물리 판정은 없다.
2.5D 화면의 원근과 도형 높이는 표현에만 사용한다. 프레임 수나 렌더링 속도가 게임 규칙을 바꾸지 않아야 한다.

### 3.2 기본 지형과 물건

| 기호 | 지형 또는 초기 배치 | 초기 동적 상태 |
| --- | --- | --- |
| `#` | 벽 | 통행 불가 |
| `.` | 일반 바닥 | 비어 있음 |
| `@` | 시작 위치 | 플레이어, 지형은 일반 바닥 |
| `E` | 출구 | 모든 조건을 만족하면 완료 |
| `P` | 부품 위치 | 일반 바닥 위 `part` 하나 |
| `B` | 뼈 묶음 위치 | 일반 바닥 위 `bone` 하나 |
| `T` | 함정 자리 | 파손 상태 |
| `L` | 레버 | 가동 전 |
| `A` | 조립 작업대 | 납품한 뼈 묶음 0개 |
| `S` | 초소 | 병사 미배치 |
| `F` | 발판 | 플레이어 또는 바닥 물건이 누르면 연결문 열림 |
| `G` | 연결문 | 발판에 따라 열림·닫힘·닫힘 대기 판정 |
| `C` | 뼈 투입구 | 연결된 출력칸으로 뼈 묶음 전송 |
| `O` | 표시된 배출구 | 연결 투입구가 보낸 뼈의 도착 위치 |
| `^ v < >` | 위·아래·왼쪽·오른쪽 운반 벨트 | 성공 행동 뒤 끝이나 장애물까지 자동 운반. B 대기 없음, 순환 경로 금지 |

원본 맵은 변경하지 않는다. 줍거나 내려놓은 물건은 별도의 동적 목록에서 관리한다. 시작 위치에 다시 돌아올 수 있다. 시작 표식은 충돌 지형이 아니다.
프로토타입의 레버는 같은 방의 모든 함정을 한 번에 가동한다.

### 3.3 점유 매트릭스

| 대상 칸 상태 | 플레이어 진입 | 현재 칸에서 물건 줍기 | 일반 내려놓기 `Q` |
| --- | --- | --- | --- |
| 빈 일반 바닥 | 가능 | 대상 없음 | 가능 |
| 일반 바닥 위 물건 | 가능 | 빈손이면 가능 | 불가: 기존 물건 있음 |
| 파손 함정 | 가능 | 기본 데이터에서는 물건 없음 | 불가: 설치 동작 사용 |
| 설치 완료·미가동 함정 | 가능 | 기본 데이터에서는 물건 없음 | 불가 |
| 가동 함정 | 불가 | 진입할 수 없음 | 불가 |
| 빈 초소 | 가능 | 대상 없음 | 불가: 배치 동작 사용 |
| 병사 배치 초소 | 새 진입 불가 | 직접 회수 불가 | 불가 |
| 작업대·레버·출구 | 가능 | 기본 데이터에서는 물건 없음 | 불가 |
| 발판·배출구 | 가능 | 빈손이면 가능 | 빈칸이면 가능 |
| 열린 연결문 | 가능 | 빈손이면 가능 | 빈칸이면 가능 |
| 닫힘 대기 연결문 | 새 진입 불가, 현재 점유자는 이탈 가능 | 현재 칸에서 빈손이면 가능 | 현재 칸에 물건이 없으면 가능 |
| 닫힌 연결문 | 불가 | 진입할 수 없음 | 불가 |
| 뼈 투입구 | 가능 | 뼈 전송 동작 사용 | 불가 |
| 운반 벨트 | 가능 | 빈손이면 가능 | 부품·조립 병사만 가능, 뼈는 불가 |
| 벽·보드 밖 | 불가 | 불가 | 불가 |

배치 동작은 플레이어가 서 있는 초소에서 일어난다. 따라서 배치 직후 플레이어와 병사가 한 칸에 잠시 함께 있을 수 있다.
플레이어는 이 칸에서 나갈 수 있지만, 나간 뒤에는 다시 들어갈 수 없다. 닫힘 대기 문도 현재 점유자를 보존하고 새 진입만 막는다. 그 외 일반 이동의 진입 차단 규칙은 유지한다.
물건 위로 이동하는 것은 물건을 줍는 행동이 아니다. 줍기는 별도 입력으로 실행한다.

## 4. 행동 규칙과 상태 전이

### 4.1 조작 계약

| 입력 | 행동 | 완료 후 허용 |
| --- | --- | --- |
| 마우스 왼쪽 클릭 | 바닥·물건·장치에 대응하는 칸까지 최단 경로 이동 | 아니요 |
| 마우스 오른쪽 클릭 | 남은 자동 이동 경로 취소 | 예 |
| 방향키 / `W A S D` | 위·왼쪽·아래·오른쪽 한 칸 이동 | 아니요 |
| `E` / `Space` | 현재 칸의 물건 또는 장치와 상호작용 | 아니요 |
| `Q` | 일반 바닥·발판·배출구·문 칸에 내려놓기, 벨트에는 부품·병사만 | 아니요 |
| `B` | 한 행동 대기하여 벨트 진행 | 아니요 |
| `Z` / `Backspace` | 직전 유효 행동 되돌리기 | 예 |
| `R` | 현재 방 재시작 | 예 |
| `Enter` | 완료한 방에서 다음 방 진행 | 예 |
| `Escape` / 창 닫기 | 게임 종료 | 예 |

사선 화면에서 `W/위`는 화면 오른쪽 위, `D/오른쪽`은 오른쪽 아래, `S/아래`는 왼쪽 아래, `A/왼쪽`은 왼쪽 위다. 키보드의 논리 방향과 기존 행동 이름은 바꾸지 않는다.
논리 모델에는 바라보는 방향 상태가 없다. 캐릭터의 방향 그림은 표시 상태이며, 상호작용은 앞 칸이 아닌 플레이어가 서 있는 현재 칸을 대상으로 한다.
따라서 벽 쪽 방향키를 눌러도 숨은 방향 상태나 행동 기록이 변하지 않는다. 키를 누르고 있을 때의 반복 속도는 UI 문제로 다루고, 모델에는 한 번에 한 행동만 전달한다.
클릭 이동 중에도 각 한 칸 이동은 독립된 되돌리기 단위다. 키보드 입력은 남은 자동 이동을 취소한 뒤 기존 키 동작을 실행한다.

#### 클릭 이동 규칙

0.6에서는 바닥뿐 아니라 물건·장치의 표시 위치를 클릭해 해당 논리 칸을 목적지로 정한다. 마우스를 올린 칸에 대해 경로 미리보기와 목표 표시를 제공한다. 클릭은 이동 요청이며 줍기·설치·납품·레버 가동을 자동 실행하지 않는다.

1. 현재 통행 가능한 칸으로 최단 경로를 찾는다. 목표가 막혀 있거나 도달할 수 없으면 이동을 시작하지 않는다.
2. 예약한 경로를 약 0.18초 간격으로 한 칸씩 기존 `Game.act()`에 전달한다. 위치를 목적지로 한 번에 옮기지 않는다.
3. 성공한 한 칸마다 행동 수와 되돌리기 기록이 하나 늘고 벨트가 한 번 처리된다. 경로 전체를 되돌리기 한 번으로 묶지 않는다.
4. 다음 칸에 진입하기 전에 현재 상태로 이동을 판정한다. 문·병사·가동 함정 등으로 통로가 막히면 남은 경로를 중단한다. 새 목적지를 클릭하면 현재 상태에서 경로를 다시 찾는다.
5. 오른쪽 클릭 또는 키보드 입력으로 남은 경로를 취소한다. 취소 자체는 이미 실행한 이동과 벨트 결과를 되돌리지 않는다. 키보드는 취소 후 해당 키 동작을 실행하므로 `Z` 또는 `Backspace`는 직전 한 행동을 복원한다.
6. 현재 칸 클릭은 이동·행동 수·벨트 처리를 만들지 않는다. UI와 맵 바깥 클릭은 무시한다.
7. 경로 중간의 출구에서 완료 조건을 만족하면 즉시 자동 이동을 멈춘다. 되돌리기·재시작·방 전환 때에도 이전 경로를 이어 실행하지 않는다.

예약 경로·마우스 위치·미리보기는 입력 및 표시 상태다. 퍼즐 상태에 새로운 자동 이동 명령이나 순간 이동 규칙을 추가하지 않는다. 여섯 방의 데이터와 복구·장치 규칙은 유지한다.

### 4.2 상호작용의 우선순위

현재 칸에서 아래 조건을 순서대로 확인한다. 실행 가능한 동작 하나만 수행한다.

1. 완료된 방이면 일반 행동을 막고 다음 방·되돌리기·재시작을 안내한다.
2. 현재 칸에 느슨한 물건이 있으면 빈손일 때 줍는다. 손이 차 있으면 실패한다.
3. 투입구에서 뼈를 들고 있고 출력칸이 비어 있으면 뼈 묶음 하나를 전송한다.
4. 함정 자리에서 부품을 들고 있고 아직 설치하지 않았으면 설치한다.
5. 작업대에서 뼈 묶음을 들고 있으면 조립 재료로 납품한다.
6. 빈 초소에서 병사를 들고 있으면 병사를 배치한다.
7. 레버에서 빈손이고 가동 조건이 맞으면 함정을 가동한다.
8. 해당하는 동작이 없으면 필요한 대상 또는 불가 사유만 표시한다.

지형 기호는 한 칸에 하나이므로 작업대와 레버 같은 고정 장치는 겹치지 않는다. 현재 칸의 행동 안내와 실제 실행은 같은 조건을 사용해야 한다.
UI에 가능하다고 표시한 행동이 실행 시 실패하면 규칙 또는 안내의 결함으로 기록한다.

### 4.3 운반과 내려놓기

손에는 `part`, `bone`, `soldier` 중 하나만 담는다. 가방, 중첩 수량, 자동 줍기는 제공하지 않는다.
물건을 주우면 바닥 목록에서 제거하고 손에 담는다. 물건을 내려놓으면 손을 비우고 현재 칸에 같은 종류 하나를 만든다. 일반 바닥 외에 발판·배출구·플레이어가 서 있는 문 칸에서도 내려놓을 수 있다.
이미 물건이 있거나 함정·초소·작업대·레버·투입구·출구인 칸에서는 내려놓을 수 없다. 손이 빈 상태의 `Q`는 실패 행동이다.
벨트 위에는 부품·조립 병사만 내려놓을 수 있다. 뼈 내려놓기는 실패하며 상태와 벨트가 진행되지 않는다. 성공적으로 내려놓은 물건은 같은 행동의 벨트 처리 대상이 될 수 있다.
설치한 부품과 배치한 병사는 일반 물건이 아니며 직접 회수하지 않는다. 설치·배치 선택을 고치는 경로는 되돌리기 또는 재시작이다.

### 4.4 함정 복구

| 이전 상태 | 조건과 행동 | 이후 상태 | 통행 |
| --- | --- | --- | --- |
| 파손 | 해당 칸에서 부품을 들고 상호작용 | 설치 완료, 손 비움 | 가능 |
| 설치 완료 | 레버에서 가동 조건 충족 | 가동 | 불가 |
| 가동 | 일반 상호작용 | 변경 없음 | 불가 |
| 모든 상태 | 되돌리기 | 직전 스냅숏 상태 | 복원 상태에 따름 |

레버 가동 조건은 빈손, 모든 함정 설치 완료, 아직 미가동, 함정 위에 느슨한 물건 없음이다. 함정은 가동 후 끌 수 없다. 가동 취소는 되돌리기로 처리한다.
가동 함정은 접촉 피해 대신 이동 차단으로 표현한다. 생명 수·사망·무적 시간은 프로토타입에서 도입하지 않는다.
레버 위치와 함정 위치는 서로 다른 칸이므로 가동 입력으로 플레이어가 함정 안에 갇히지 않는다. 다만 남은 작업의 접근 경로는 끊길 수 있다. 이것이 순서 퍼즐의 실패 상황이다.
함정이 없는 방은 함정 관련 완료 조건을 자동 충족한다.

### 4.5 뼈 납품과 병사 조립

프로토타입 결정: 병사 한 명에 뼈 묶음 두 개가 필요하다. 이는 해부학적 뼈 수가 아니라 운반해야 할 재료 단위다.
각 작업대는 납품된 묶음 수를 별도로 보관한다.

| 이전 상태 | 입력 | 결과 |
| --- | --- | --- |
| 작업대 0개, 손에 뼈 | 상호작용 | 작업대 1개, 손 비움 |
| 작업대 1개, 손에 뼈 | 상호작용 | 작업대 0개, 손에 조립 병사 |
| 손에 부품·병사 또는 빈손 | 상호작용 | 납품·조립 없음, 안내만 표시 |

두 번째 납품과 병사 생성은 하나의 행동이다. 중간에 뼈 두 개가 모두 사라지고 병사가 아직 없는 상태를 노출하지 않는다.
작업대에 한 개 납품한 상태도 되돌리기로 복원한다. 조립 병사는 손에 생성되므로 작업대 주변 빈칸 여부가 조립 조건에 영향을 주지 않는다.
작업대를 여러 개 두는 후속 방에서는 재료를 나누어 넣어 막힐 수 있다. 현재 입문방은 작업대 하나로 조립 규칙을 먼저 검증한다.

### 4.6 병사 배치

초소에 서서 조립 병사를 든 상태로 상호작용하면 배치한다. 손에서 병사를 제거하고 해당 초소를 배치 완료로 표시한다.
배치된 병사는 움직이지 않고 그 칸으로의 새 진입을 막는다. 초소가 아닌 곳의 `Q`는 병사를 일반 물건으로 내려놓는 행동이다. 목표 완료로 세지 않는다.
배치 후 직접 회수를 허용하지 않아, 통로를 막는 시점에 판단이 필요하다. 병사가 없는 방은 병사 관련 완료 조건을 자동 충족한다.

### 4.7 완료 판정과 다음 방

아래 조건을 모두 만족한 유효 행동 직후 완료로 전환한다.

1. 모든 함정이 설치되고 가동되어 있다. 함정이 없으면 충족한다.
2. 모든 초소에 병사가 배치되어 있다. 초소가 없으면 충족한다.
3. 플레이어가 출구 칸에 서 있다.
4. 플레이어의 손이 비어 있다.

완료 전 출구 칸은 일반 이동 가능한 칸이다. 도착만으로 강제 이동하거나 초기화하지 않는다. 완료 시 보드와 완료 요약을 유지하고 다음 입력을 기다린다.
완료 후 이동·상호작용·내려놓기는 막되, 되돌리기와 재시작은 허용한다. 다음 방으로 이동할 때 새 게임 상태를 생성하고 이전 방의 되돌리기 기록을 넘기지 않는다.
마지막 방은 전체 프로토타입 완료를 명확히 표시한다. 없는 네 번째 방을 요청하지 않는다.

## 5. 실패, 되돌리기, 재시작

### 5.1 실패 행동의 원칙

| 상황 | 사용자 안내의 핵심 | 보존할 상태 |
| --- | --- | --- |
| 벽·경계로 이동 | 이동할 수 없음 | 위치, 물건, 목표, 행동 수, 기록 |
| 가동 함정으로 이동 | 함정이 길을 막음 | 동일 |
| 병사 칸으로 진입 | 배치된 병사가 길을 막음 | 동일 |
| 손이 찬 상태에서 줍기 | 먼저 내려놓아야 함 | 동일 |
| 맞지 않는 재료로 작업 | 필요한 재료 이름 | 동일 |
| 복구 미완료 상태의 레버 | 먼저 모든 함정 설치 | 동일 |
| 내려놓기 금지 장치 위 입력 | 일반 바닥·발판·배출구 등 허용 칸으로 이동 | 동일 |
| 투입구의 잘못된 재료·막힌 출력 | 뼈만 전송, 출력 점유 해소 | 동일 |
| 되돌릴 기록 없음 | 되돌릴 행동 없음 | 동일 |

실패는 안내 메시지만 바꾼다. 행동 수와 되돌리기 기록은 늘리지 않는다. 숨은 자동 이동, 재료 소비, 부분 설치가 일어나지 않아야 한다.
모델의 잘못된 행동 이름은 사용자 실패와 구별하여 개발 오류로 알린다.

### 5.2 되돌리기의 원자성

성공할 상태 변경이 확인되면 변경 전 상태 전체를 깊은 복사로 보관한다. 보관 대상은 위치, 손, 바닥 물건, 설치 함정, 가동 여부, 배치 병사, 작업대 재료, 행동 수, 완료 여부다.
되돌리기 한 번은 이 스냅숏 하나를 복원한다. 조립처럼 재료 소비와 새 물건 생성이 묶인 행동도 한 번에 복원한다.
UI 메시지와 화면 애니메이션은 규칙 상태가 아니므로 과거 문구를 그대로 재생할 필요는 없다. 되돌린 뒤 다른 행동을 하면 새 경로로 이어진다. 다시 실행하기 기능은 이번 범위에 없다.
무제한 되돌리기를 제공한다. 작은 방과 짧은 상태 구조에서 우선 명료성을 선택한다. 후속 대규모 상태에서 메모리 문제가 실측될 때만 차분 기록으로 바꾼다.

### 5.3 재시작

현재 상태를 역으로 수정하지 않고 원본 방 데이터에서 새 초기 상태를 만든다. 위치·물건·작업대·함정·초소·행동 수·완료 여부를 초기화한다.
되돌리기 기록도 비운다. 재시작 이전 상태로 되돌릴 수는 없다. 재시작 자체는 퍼즐 행동 수에 포함하지 않는다.
초기 상태가 원본 맵과 독립적인 객체인지 검사하여 원본 변형을 방지한다.

## 6. 스테이지별 상세 설계

### 6.1 현재 입문 세 방의 역할

현재 1~6번 방은 모두 10×10 보드다. 2026-11-09 크기 조정으로 기존 12×12에서 빈 통로를 줄여 전체 보드 면적을 144칸에서 100칸으로 축소했다. 후속 7~8번 방은 12×12로 설계한다. 아래 내용은 학습 목표와 배치 원칙이며, 실제 좌표는 `data/stages.json`을 기준으로 한다.
구현된 방 이름이나 이동 수를 이 문서에 중복 고정하지 않아 데이터 수정에 따른 불일치를 줄인다. 정답 행동열은 테스트에 두고 플레이 화면에서는 노출하지 않는다.

| 방 ID | 현재 데이터의 구조 | 검증할 차이 |
| --- | --- | --- |
| `stage_01` | 북쪽 입구의 부품, 동쪽 통로의 함정, 남쪽 제어실의 레버와 출구 | 구역을 오가는 운반, 가동 함정 진입 차단과 서쪽 우회 |
| `stage_02` | 동쪽 두 보관실의 뼈 묶음, 서쪽 작업대, 동서 연결부의 초소 | 두 재료 회수와 조립·배치, 배치 후 동쪽 구역 진입 차단 |
| `stage_03` | 서쪽 작업 구역과 동쪽 위·아래 복구 구역, 각 연결부에 초소와 함정 | 두 함정 설치·병사 두 명 배치, 구역별 재료 회수 후 최종 차단 |

첫 방은 넓은 순환 동선에서 함정 복구 절차를 익힌다. 둘째 방은 한 초소가 재료 보관 구역의 입구를 막고, 셋째 방은 서로 분리된 두 구역의 설치·회수·배치 순서를 조합한다. 크기만 늘린 빈 공간이 되지 않도록 각 구역에 운반 목적과 차단 결과를 부여한다.

### 6.2 1단계: 함정 복구 입문

- 학습 목표: 부품을 밟아도 자동으로 줍지 않는다는 점과 설치·가동의 차이를 익힌다.
- 핵심 오브젝트: 부품 한 개, 함정 한 개, 레버, 출구.
- 배치 원칙: 시작 부근에 부품을 두고 동쪽 통로까지 운반한 뒤 남쪽 제어실에서 가동하게 한다. 서쪽에는 우회 동선을 남겨 첫 방에서 회복 불가능한 막힘을 강요하지 않는다.
- 판단: 설치를 완료한 뒤 가동 상태에서는 해당 칸에 들어갈 수 없음을 확인한다.
- 해결 흐름: 부품 줍기, 함정 칸으로 운반, 설치, 레버로 이동, 가동, 빈손 출구.
- 예상 실수: 부품 없이 설치 시도, 설치 전 레버 사용, 가동 함정 재진입.
- 안내: 설치 전에는 필요한 부품을, 설치 후에는 레버를 안내한다.
- 통과 기준: 처음 시작한 상태부터 완료까지 자동 행동열로 재생된다.
- 추가 검사: 설치 직후와 가동 직후 각각 되돌려 위치·손·함정 상태가 복원된다.
- 최종 입문방 보완: 가동 이후 차단이 시각적으로 뚜렷한 배치를 선택한다.

### 6.3 2단계: 병사 조립 입문

- 학습 목표: 두 번의 재료 운반, 작업대 보관, 조립 병사 운반, 초소 배치를 익힌다.
- 핵심 오브젝트: 뼈 묶음 두 개, 작업대 하나, 초소 하나, 출구.
- 배치 원칙: 작업대는 서쪽, 두 뼈 묶음은 동쪽 위·아래 보관실에 둔다. 동서 연결부의 초소를 채우기 전에 두 재료를 회수하게 한다.
- 판단: 손이 비어야 다음 뼈를 주울 수 있으며, 완성 병사도 운반 대상이라는 점을 배운다.
- 해결 흐름: 첫 뼈 납품, 둘째 뼈 납품과 조립, 초소로 운반, 배치, 출구.
- 예상 실수: 뼈를 직접 초소에 납품, 병사를 일반 바닥에 내려놓고 완료로 오해.
- 안내: 작업대에 `1/2`, 초소에 미배치·배치 상태를 보여준다.
- 통과 기준: 뼈가 남거나 병사가 중복 생성되지 않고 완료된다.
- 추가 검사: 둘째 납품을 되돌리면 첫 납품과 손의 둘째 뼈가 모두 복원된다.
- 최종 입문방 보완: 배치가 통로를 막는 효과를 확인하되 첫 실수 복구가 짧게 끝나게 한다.

### 6.4 3단계: 복구 순서와 복귀

- 학습 목표: 함정과 병사를 따로 완성하는 것 외에 남은 경로를 계획해야 함을 익힌다.
- 핵심 오브젝트: 부품 두 개·함정 두 개·레버 하나와 뼈 네 묶음·작업대 하나·초소 두 개를 함께 둔다.
- 배치 원칙: 동쪽 위·아래 구역을 서로 분리하고, 각 구역으로 향하는 좁은 연결부에 초소와 함정을 연달아 둔다.
- 현재 데이터: 동쪽 각 구역에 부품 하나와 뼈 두 묶음, 서쪽 공용 구역에 작업대·레버·출구를 둔다. 한 구역의 설치·재료 회수가 끝나면 해당 초소를 채우고 다른 구역을 처리할 수 있다.
- 판단: 차단 뒤에도 필요한 모든 재료를 확보했고 출구 쪽으로 복귀할 수 있는지 확인한다.
- 해결 원칙: 각 초소를 채우기 전에 해당 구역의 함정 설치와 두 뼈 회수를 마친다. 두 함정을 모두 설치한 뒤에만 공용 레버로 가동할 수 있다.
- 예상 실수: 함정을 너무 일찍 가동하거나 초소에서 잘못된 방향으로 빠져나와 남은 작업을 차단.
- 안내: 정답 순서를 직접 제시하지 않고 남은 작업 수와 통행 차단 상태를 표시한다.
- 통과 기준: 정상 해결 경로와 조기 차단으로 막히는 경로가 모두 재현된다.
- 추가 검사: 막힌 상태에서 되돌리면 다시 접근할 수 있고 정상 해결로 이어진다.
- 최종 입문방 보완: 차단을 피하는 우회로가 의도치 않게 모든 판단을 없애지 않는지 검토한다.

### 6.5 4단계: 발판과 연결문 — 구현한 응용방 프로토타입

- 학습 목표: 물건의 위치가 통로 개폐 조건이 될 수 있음을 익힌다.
- 적용 규칙: 발판 위 플레이어 또는 느슨한 운반물이 연결문을 연다.
- 배치 원칙: 발판·연결문을 동시에 볼 수 있게 하고 첫 작동은 안전한 왕복 통로에서 보여준다.
- 판단: 재료를 바로 소비할지, 잠시 발판의 추로 사용할지 선택한다.
- 예상 실수: 문을 연 물건을 주워 통로가 닫힘, 필요한 재료를 문 반대편에 남김.
- 해결 가능성 검사: 추 역할과 복구 재료 역할이 충돌해도 순서를 바꾸면 해결 가능해야 한다.
- 필수 검증: 문 위 플레이어·물건이 있을 때 닫힘 정책, 발판 해제와 되돌리기의 일관성.
- 현재 상태: `stage_04`에서 부품을 발판에 내려놓아 문을 열고, 뼈를 회수한 뒤 부품을 되찾아 함정을 복구한다. 최종 난이도와 플레이 시간은 미확정이다.

### 6.6 5단계: 뼈 투입구 — 구현한 응용방 프로토타입

- 학습 목표: 플레이어와 재료가 서로 다른 경로를 사용할 수 있음을 익힌다.
- 새 규칙: 뼈만 벽 너머 지정 출력칸으로 보낼 수 있다.
- 배치 원칙: 투입구와 출력칸을 대응 표식으로 연결하고, 출력 위치를 화면에서 확인할 수 있게 한다.
- 판단: 뼈를 직접 운반할지 전송할지보다, 어느 쪽 작업대에 언제 전달할지 계획한다.
- 예상 실수: 부품·병사 투입 시도, 출력칸이 찬 상태에서 전송 시도.
- 해결 가능성 검사: 전송된 뼈를 회수할 플레이어의 경로가 존재해야 한다.
- 필수 검증: 막힌 출력에서 재료 유지, 한 번의 전송과 undo, 출력 덮어쓰기 금지.
- 현재 상태: `stage_05`에서 뼈를 벽 너머 발판으로 전송해 문을 연 뒤, 건너가 뼈를 회수하고 병사를 조립한다. 최종 난이도와 플레이 시간은 미확정이다.

### 6.7 6단계: 운반 벨트 — 응용방 프로토타입

- 학습 목표: 플레이어 행동 뒤 물건이 한 칸 이동하는 결과를 예측한다.
- 새 규칙: 부품·조립 병사를 벨트 방향으로 최대 한 칸 운반한다. 뼈는 운반하지 않는다.
- 배치 원칙: 처음에는 벨트 하나와 비어 있는 목적지만 둔 뒤 짧은 연결 구간을 추가한다.
- 판단: 물건을 언제 올리고 언제 회수해야 원하는 위치에 남는지 계산한다.
- 예상 실수: 뼈도 움직일 것으로 예상, 연속 벨트에서 한 턴에 끝까지 이동할 것으로 예상.
- 해결 가능성 검사: 자동 이동을 기다릴 수단과 필요한 회수 경로가 있어야 한다.
- 필수 검증: 한 턴 최대 한 칸, 충돌 시 유지, 목록 순서와 무관한 결과.
- 적용 규칙: `B`로 한 행동 대기하고, 성공한 모든 행동 뒤 벨트가 한 번 진행한다. `stage_06`에서 벨트의 한 칸 운반과 회수 시점을 다룬다. 최종 난이도와 플레이 시간은 미확정이다.

### 6.8 7단계: 보조 장치 결합 — 후속 제안

- 학습 목표: 투입구·벨트·발판의 역할을 구분하면서 재료와 통로를 함께 계획한다.
- 배치 원칙: 세 장치를 모두 쓰더라도 각 장치의 입출력 관계가 겹쳐 보이지 않게 한다.
- 판단: 부품을 추로 쓰는 시점, 뼈를 전송하는 시점, 병사를 벨트에서 회수하는 시점을 선택한다.
- 예상 실수: 재료를 목표에 너무 빨리 소비하여 발판을 누를 수단을 잃음.
- 해결 가능성 검사: 모든 장치가 실제 해결에 기여하는지 확인하고 장식성 장치는 제거한다.
- 필수 검증: 한 행동으로 여러 상태가 변해도 undo 한 번으로 전부 복원한다.
- 난이도 조절: 장치 수보다 공유 재료와 한 방향 통로의 수로 조절한다.
- 현재 상태: 개별 보조 장치의 규칙이 검증된 뒤 좌표를 확정한다.

### 6.9 8단계: 전체 복구 — 후속 제안

- 학습 목표: 새 규칙 없이 기존 규칙을 조합하여 전체 작업 순서를 세운다.
- 배치 원칙: 재료 확보, 우회 운반, 병사 배치, 출구 복귀, 최종 가동의 작업 구역을 읽을 수 있게 한다.
- 판단: 되돌아갈 수 없는 배치·가동을 어느 시점까지 미룰지 결정한다.
- 예상 실수: 일부 목표만 보고 전체 운반 경로를 닫음.
- 해결 가능성 검사: 완전한 정답 행동열뿐 아니라 구역별 중간 상태를 기록한다.
- 필수 검증: 모든 목표 조합, 마지막 가동 후 출구, 완료 undo, 장시간 플레이 후 재시작.
- 난이도 조절: 새 규칙을 추가하지 않고 의존 관계의 수와 작업 순서의 깊이를 조절한다.
- 현재 상태: 1~7단계 플레이테스트를 통과한 규칙만 사용한다.

## 7. 보조 장치 규칙

이 절은 발판·연결문, 뼈 투입구, 벨트의 프로토타입 규칙이다. 장치 구현과 본편 8개 방의 완성은 구분한다. 실제 기능별 검사 결과는 개발 기록에 남긴다.

### 7.1 발판과 연결문

발판 `F`와 문 `G`는 `plate_links`의 명시적인 연결 ID와 좌표로 1:1 대응시킨다. 좌표가 가깝다는 이유로 자동 연결하지 않는다. 플레이어 또는 바닥 물건이 발판을 누르면 문이 열리고, 문은 열림·닫힘·닫힘 대기 상태를 구별한다.
발판이 해제되어도 문 칸에 플레이어나 물건이 있으면 닫힘 대기 상태로 두고 진입은 차단한다. 점유자가 나가면 닫는다. 끼인 대상의 삭제·강제 이동은 하지 않는다.
복수 발판의 AND·OR 연결은 첫 구현에서 도입하지 않고 문 하나에 발판 하나로 시작한다. 연결 규칙이 늘면 레벨 데이터 검증과 화면 연결 표시를 함께 늘린다.

### 7.2 뼈 투입구

투입구 `C` 칸에서 뼈를 들고 `E` 또는 `Space`로 전송한다. `chute_links`의 ID와 좌표로 입력·출력을 연결하며, 출력칸은 표시된 배출구 `O`, 일반 바닥 `.`, 발판 `F` 중 하나여야 한다. 발판으로 뼈를 보내 연결문을 여는 조합을 허용한다.
출력칸에 플레이어 또는 느슨한 물건이 있으면 전송을 거절한다. 성공 시 손의 뼈 하나를 제거하고 출력칸에 뼈 하나를 둔다.
실패 시 손·출력·행동 수·기록을 그대로 유지한다. 입력과 출력은 하나의 행동으로 처리하고 undo 한 번으로 복원한다.
투입구끼리 연쇄 전송하는 규칙은 도입하지 않는다.

### 7.3 벨트의 한 칸 운반

턴 단위는 플레이어의 성공한 행동 또는 `B` 대기 한 번이다. 대기도 행동 수와 되돌리기 기록에 포함한다. 실패 입력·UI 조작·되돌리기·재시작은 벨트를 진행시키지 않는다.
벨트 기호 `^ v < >`는 논리 보드의 위·아래·왼쪽·오른쪽을 나타내고 `Level.belts`에 위치와 방향을 보관한다. 플레이어 행동을 적용한 직후의 점유 상태에서 이동 후보를 먼저 수집한다. 목적지가 벽·범위 밖·닫힌 문·닫힘 대기 문·가동 함정·배치 병사·플레이어·다른 물건이면 이동하지 않는다.
둘 이상의 물건이 같은 목적지를 요구하면 모두 제자리에 둔다. 현재 다른 물건이 있는 목적지는 그 물건도 이동할 예정이더라도 막힌 것으로 처리한다.
이 보수적인 규칙은 연쇄 이동과 서로 자리 바꾸기를 금지하여 순서 의존성을 줄인다. 벨트에서 옮겨진 물건은 같은 턴의 다음 벨트 후보에 다시 넣지 않는다.
운반 대상은 느슨한 부품·조립 병사이며, 플레이어·배치 병사·뼈는 움직이지 않는다. 빈 벨트 칸에는 부품·조립 병사를 `Q`로 내려놓을 수 있고 뼈는 내려놓을 수 없다.

### 7.4 여러 장치가 연동되는 턴

1. 플레이어 행동의 유효성을 확인하고 변경 전 상태를 보관한다.
2. 플레이어의 이동·운반·직접 장치 동작을 적용한다.
3. 현재 점유로 발판과 문의 상태를 계산한다.
4. 벨트 이동 후보를 모으고 충돌 판정 후 동시에 적용한다.
5. 벨트로 달라진 점유에 따라 발판과 문 상태를 다시 계산한다.
6. 완료 조건과 상태 불변식을 검사하고 행동 하나를 확정한다.

재평가 때문에 벨트를 다시 실행하지 않는다. 한 턴에 벨트 처리는 한 번이다. 행동 후보 상태에서 직접 동작과 자동 장치 처리를 마친 뒤 확정하여 실패·예외가 원본 상태의 일부만 변경하지 않게 한다. 되돌리기는 같은 행동에서 일어난 벨트 이동과 발판·문 결과까지 함께 복원한다.

## 8. 화면, 조작 안내, 표현 계획

### 8.1 화면 구성

프로토타입 해상도는 1600×960이다. 상하단 안내 영역을 줄여 현재 10×10 방의 타일을 120×60으로 표시한다. 기존 96×48보다 가로세로 25% 크며, 캐릭터·장치도 같은 비율로 확대한다. 좌표는 기본으로 숨기고 F2로 표시한다.
상단 HUD에는 게임명·현재 방 번호·방 제목과 운반물·함정 설치 및 가동·병사 배치·행동 수를 모은다. 하단에는 현재 가능한 행동과 최근 행동 결과, 조작 안내를 표시한다. 목표별 진행을 각각 표시하여 진행률 하나로 뭉개지 않는다.
완료 안내가 떠도 퍼즐의 최종 상태를 볼 수 있게 한다. 긴 안내는 보드 위를 덮는 대화창보다 고정 문구 영역에서 줄바꿈한다.
0.6에서는 마우스 위치에 따른 이동 경로와 목표 칸을 보드에 표시한다. 장치의 상태 문구와 운반물을 가리지 않도록 경로 표시는 바닥을 따라 그린다.

### 8.2 2.5D 투영

정면 3/4·탑다운 실험을 철회하고 기존 사선 시점·원본 에셋 표시로 복귀했다. 2026-11-09의 1번 방 동선 압축, 높은 외곽 벽과 통행 불가 석축 표현은 유지한다. 탑다운 에셋은 보존용이며 실행에는 사용하지 않는다. 클릭 이동으로 목적지를 지정한다.

화면 바닥 중심을 `(origin_x, origin_y)`, 타일 폭·높이를 `tile_w`, `tile_h`로 둔다. 논리 칸 `(x, y)`의 화면 기준점은 다음 식을 기준으로 구현할 수 있다.

```text
screen_x = origin_x + (x - y) * tile_w / 2
screen_y = origin_y - (x + y) * tile_h / 2
```

pico2d의 화면 y축과 논리 보드의 y축 방향이 다르므로 두 좌표를 혼용하지 않는다. 최종 원점·타일 크기는 방 전체와 UI가 겹치지 않는지 보고 정한다.
화면 크기와 보드 표시 영역은 `game/layout.py`에서 공유한다. 보드는 화면 y=94~830 사이에 배치하며, 높은 뒤쪽 벽까지 들어오도록 방 크기에 따라 타일 크기를 계산한다. 타일 반폭 상한은 64이며 현재 10×10 방에서는 60이다. 정확한 원점과 투영은 `game/navigation.py`의 `IsoBoard`, UI 배치는 `game/view.py`를 기준으로 한다.
바닥을 먼저 그리고 물건·장치를 깊이 순으로 그려 앞쪽 물체가 뒤쪽 물체를 가리게 한다. 그림자의 크기와 높이는 충돌 범위가 아니다. 이동 가능한 칸은 바닥 윤곽으로 읽히게 한다.
선택 칸과 플레이어 발밑은 다른 물체에 가려도 위치를 알 수 있게 표시한다.

### 8.3 상태를 구별하는 시각 언어

| 요소 | 최소 구별 기준 | 후속 아트 요구 |
| --- | --- | --- |
| 부품 | 기계 부품 형태와 이름 | 작은 크기에서도 뼈와 구별 |
| 뼈 | 밝은 뼈 형태 | 두 묶음 규칙을 설명하는 재료 단위 |
| 병사 | 머리·몸통 실루엣 | 운반 중과 배치 후 자세 구별 |
| 함정 | 파손·설치·가동의 기호 및 형태 변화 | 색상 외에 가시의 높이·작동 표시 |
| 초소 | 빈 자리 윤곽 | 병사가 올라가도 목표 위치 식별 |
| 레버 | 손잡이 각도와 상태 문구 | 가동 여부 즉시 판독 |
| 작업대 | 납품 수 `0/2`, `1/2` | 진행 정보가 물체에 가려지지 않음 |
| 출구 | 고유 표식 | 목표 준비·미준비 차이 표시 |

초기 프로토타입은 기하도형과 텍스트로 위 구별을 검증했다. 현재는 1차 제작한 2.5D 에셋과 상태 문구를 함께 사용하며, 0.3의 맵 확장에서도 같은 에셋을 유지한다. 0.4에서는 벽 일부를 기존 잔해 아트로 표현하고, 일반 바닥 균열·함정 주변 그을음·돌의 색 차이·녹슨 문틀을 추가한다. 파손 패턴은 좌표에 고정되어 되돌리기와 재시작으로 바뀌지 않는다. 장치·캐릭터에는 배경 색 변조를 적용하지 않으며, 잔해의 충돌은 원래 벽과 동일하다. 최종 캐릭터·타일·효과음은 별도 제작 또는 출처와 이용 조건이 확인된 자산을 사용한다.
사용자의 PPT·발표 영상은 원본 자료로 보존하고 게임 자산으로 임의 변환하지 않는다.

### 8.4 접근성과 사용성

- 색만으로 상태를 전달하지 않고 문자·형태·수량을 함께 사용한다.
- 한글 글꼴을 확보하고 누락되면 실행 오류 또는 대체 방식의 원인을 알린다.
- Windows에서는 맑은 고딕 등 사용 가능한 로컬 한글 글꼴을 찾는다.
- `DUNGEON_FONT` 환경 변수로 한글 TTF/TTC 파일 경로를 지정할 수 있게 한다.
- 키보드만으로 모든 기초 플레이가 가능해야 한다.
- 마우스 클릭으로 이동 목적지를 선택할 수 있어야 하며, 키보드 상호작용과 취소 안내를 함께 제공한다.
- 반복 입력으로 여러 칸이 의도치 않게 이동하는지 실제 창에서 확인한다.
- 큰 번쩍임이나 반복적인 화면 흔들림은 기초 구현에 넣지 않는다.
- 키 변경과 확대 UI는 후속 요구가 확인되면 추가한다. 현재 지원으로 표기하지 않는다.

### 8.5 사운드와 연출 — 후속 제안

우선 필요한 소리는 줍기, 내려놓기, 설치, 조립 완료, 배치, 레버, 실패, 완료다. 같은 입력을 연속으로 실패해도 큰 소리가 반복되지 않도록 재생 간격을 제한한다.
되돌리기와 재시작은 짧고 구별되는 피드백을 주되 보드 확인을 지연시키지 않는다. 연출이 진행되는 동안 모델 상태를 여러 단계에 나누어 바꾸지 않는다.
상태 변경은 먼저 확정하고 애니메이션은 그 결과를 보여준다. 음소거와 볼륨 조절을 함께 제공하기 전에는 큰 배경 음악을 기본 재생하지 않는다.

## 9. 코드와 데이터 설계

### 9.1 최소 파일 구조와 책임

| 경로 | 책임 | 맡기지 않는 일 |
| --- | --- | --- |
| `main.py` | CLI 옵션, 데이터 검사, 게임 실행과 오류 안내 | 세부 복구 규칙 |
| `game/levels.py` | JSON 읽기, 맵 검증, 정적 방 정보 생성 | 렌더링과 플레이 상태 변경 |
| `game/model.py` | 상태, 유효 행동, undo, restart, 완료 판정 | pico2d·글꼴·화면 좌표 |
| `game/view.py` | 보드·UI 표현, 키 입력 전달, 방 진행과 창 종료 | 세부 복구 규칙 판정 |
| `data/stages.json` | 방 이름·안내·맵 | 실행 가능한 코드 |
| `tests/` | 해결 행동열, 경계 조건, 데이터 검사 | 눈으로 보는 가독성 판정 |

모델은 표준 라이브러리만으로 검사할 수 있게 한다. 그래픽 의존성은 게임 실행 경로에서만 필요하다.
엔진·에디터·ECS·이벤트 버스를 별도로 만들지 않는다. 함수 하나가 충분한 곳에 추상 클래스나 범용 플러그인 구조를 추가하지 않는다.
공통 규칙이 실제로 반복될 때만 작은 공통 함수로 묶는다.

### 9.2 상태 구조

정적 방 정보에는 ID, 제목, 안내, 원본 행, 크기, 시작·출구, 벽과 장치 위치, 초기 물건을 둔다. 가변 상태에는 플레이어, 운반물, 느슨한 물건, 설치 위치, 전체 가동 여부, 병사 위치, 작업대 재료를 둔다.
발판·문 연결, 투입구 입출력, 벨트 위치·방향은 정적 방 정보다. 발판의 눌림과 문의 열림·닫힘·닫힘 대기는 현재 플레이어와 물건 점유로 계산하므로 별도 가변 상태를 중복 저장하지 않는다.
행동 수와 완료 여부도 되돌리기 대상에 포함한다. 좌표 집합과 물건 사전은 원본과 가변 상태가 공유하지 않도록 복사한다.
스테이지가 바뀌면 새 상태를 만든다. 이전 방의 가변 객체를 재사용하지 않는다.

### 9.3 JSON 검증

검증 오류는 가능한 한 방 ID와 문제 위치를 포함한다. 아래 조건을 플레이 시작 전에 확인한다.

- 루트의 `stages`가 비어 있지 않은 목록인지 확인한다.
- 각 방의 ID·제목·안내·맵 형식과 필수 필드를 검사한다.
- ID가 중복되지 않는지 확인한다.
- 모든 행의 길이가 같고 폭·높이가 8~12인지 확인한다.
- 허용 기호만 사용하고 바깥 테두리가 벽인지 확인한다.
- 시작과 출구가 정확히 하나씩인지 확인한다.
- 최소 하나의 복구 목표가 있는지 확인한다.
- 부품 수와 함정 수가 맞는지 확인한다.
- 뼈 묶음 수가 초소 수의 두 배인지 확인한다.
- 함정이 있으면 레버, 초소가 있으면 작업대가 있는지 확인한다.
- 모든 발판 `F`와 문 `G`가 `plate_links`로 한 번씩 연결되는지 확인한다.
- 모든 투입구 `C`와 표시된 배출구 `O`가 `chute_links`에 연결되고 출력이 `O`·`.`·`F`인지 확인한다.
- 연결 ID는 중복 없는 영문 시작 1~8자이며, 좌표는 정수 두 개이고 지도 기호와 일치해야 한다.

수량 검증은 해결 가능성을 증명하지 않는다. 연결되지 않은 구역이나 잘못된 순서는 해결 행동열로 별도 확인한다. 실행 경로는 프로세스 작업 폴더가 아니라 소스 파일 위치를 기준으로 찾는다.
따라서 VS Code 실행, 저장소 루트 실행, 다른 폴더에서 절대 경로 실행이 같은 데이터를 사용해야 한다.

### 9.4 실행·점검 인터페이스

| 명령 | 용도 | 이것만으로 증명하지 못하는 것 |
| --- | --- | --- |
| `python main.py` | 첫 방에서 게임 시작 | 모든 방의 해결 가능성 |
| `python main.py --stage 3` | 지정 방부터 확인 | 앞선 방의 진행 상태 저장 |
| `python main.py --check` | 그래픽 창 없이 모든 방 데이터 검사 | 퍼즐 정답과 UI 가독성 |
| `python main.py --smoke-frames 10` | 짧게 창을 열고 종료하는 실행 검사 | 실제 입력과 사람이 느끼는 조작감 |
| `python -m unittest discover -s tests -v` | 규칙과 해결 경로 검사 | 최종 아트·화면·음향 품질 |

### 9.5 반드시 보존할 불변식

| 불변식 | 위반 예시 |
| --- | --- |
| 손에는 0개 또는 1개 | 부품을 든 채 뼈도 보유 |
| 같은 칸의 느슨한 물건은 최대 1개 | 내려놓기가 기존 물건을 덮어씀 |
| 설치 위치는 함정 집합의 부분집합 | 바닥에 함정 설치 상태가 생성됨 |
| 배치 위치는 초소 집합의 부분집합 | 일반 바닥의 병사를 완료로 계산 |
| 작업대 저장량은 0 또는 1 | 둘째 납품 후 2가 남고 병사도 생성 |
| 자원은 운반·납품·설치·배치 사이에서 보존 | undo 후 부품이나 병사 복제 |
| 실패 행동은 규칙 상태 불변 | 벽 이동이 행동 수를 증가시킴 |
| 완료 조건과 완료 표시가 일치 | 빈손이 아닌데 완료 |

자원 보존 검사는 부품과 뼈 환산량을 따로 본다. 병사 하나와 배치 병사 하나는 각각 뼈 묶음 두 개에 대응한다.
설치 부품 하나는 원래 부품 하나에 대응한다.

## 10. 검증 계획과 완료 기준

### 10.1 자동 검사

| 검사 묶음 | 대표 시나리오 | 통과 기준 |
| --- | --- | --- |
| 데이터 | 크기·기호·시작·출구·수량 오류 | 원인이 있는 오류로 거절 |
| 이동 | 벽·경계·가동 함정·병사 차단 | 상태·행동 수·기록 불변 |
| 클릭 이동 | 경로 탐색·한 칸 실행·취소·통로 변화·중간 완료 | 기존 이동 규칙과 같은 결과, 남은 경로만 안전하게 중단 |
| 운반 | 줍기·내려놓기·손 가득 참 | 중복·유실 없음 |
| 함정 | 설치 전 레버, 설치 후 가동 | 조건을 만족할 때만 가동 |
| 조립 | 첫째·둘째 납품, 잘못된 재료 | 정확히 두 묶음으로 병사 하나 |
| 배치 | 빈 초소와 일반 바닥 구별 | 초소 배치만 목표에 반영 |
| 되돌리기 | 모든 성공 행동 및 완료 | 직전 전체 상태와 동등 |
| 재시작 | 여러 행동·undo·완료 후 초기화 | 원본 초기 상태, 빈 기록 |
| 여섯 방 해결 | 고정된 정상 행동열 재생 | 여섯 방 모두 완료 |
| 순서 실패 | 조기 차단 후 undo | 막힘과 복구 모두 재현 |

테스트는 구현 문장을 그대로 따라 쓰기보다 잘못 구현했을 때 실패할 행동 결과를 확인한다. 정답 행동열에서 실패한 명령을 무시하지 않는다. 중간 행동도 성공했는지 확인한다.
실패 입력 전후의 전체 상태를 비교해 일부 필드만 바뀌는 오류를 찾는다. 여러 번 실행해도 같은 결과가 나와야 한다.

### 10.2 실제 게임 창 검사

- 첫 방이 정상 열리고 보드 전체가 화면에 들어오는지 확인한다.
- 한글 제목·안내·조작법에 깨짐이나 잘림이 없는지 확인한다.
- 각 입력이 논리 보드의 의도한 방향과 일치하는지 확인한다.
- 바닥·물건·장치 클릭이 의도한 칸을 선택하고 UI·맵 밖 왼쪽 클릭을 무시하는지 확인한다.
- 경로 미리보기·목표 표시·자동 이동 중 취소와 통로 차단을 확인한다.
- 현재 칸 상호작용 안내와 실제 결과가 일치하는지 확인한다.
- 플레이어·물건·장치가 겹칠 때 위치와 상태를 구별할 수 있는지 확인한다.
- 되돌리기·재시작 후 화면이 이전 상태로 즉시 갱신되는지 확인한다.
- 완료 뒤 다음 방 이동과 마지막 완료 화면을 확인한다.
- 창 닫기와 종료 키로 프로세스가 정상 종료되는지 확인한다.
- 다른 작업 폴더에서 실행해도 데이터·글꼴 탐색이 유지되는지 확인한다.

자동 검사 통과와 실제 창 검사를 별도로 기록한다. 창이 열렸다는 사실만으로 모든 키 입력이나 사람의 플레이 감각이 검증되었다고 쓰지 않는다.

### 10.3 기초 프로토타입 완료 조건

위 자동 검사와 가능한 실제 화면 검증의 결과를 기록한다. 실행 명령, 필요한 패키지, 조작법, 구현 범위, 미구현 항목을 README에 반영한다.
상세 계획·기능 코드·검사·실행 안내를 기능별 커밋으로 구분한다. 푸시 전에 변경 파일 목록을 확인하여 사용자 PPT 수정분과 영상이 의도치 않게 포함되지 않게 한다.
푸시 후 원격 브랜치와 로컬 커밋 일치를 확인한다. 검증하지 못한 환경과 미해결 문제는 개발 기록에 남긴다.

## 11. 6주 작업 분해와 우선순위

아래 주차는 PPT의 상대 일정이다. 실제 시작일과 제출일이 확정되면 달력 일정으로 옮긴다.

| 주차 | 작업 | 산출물 | 종료 기준 |
| --- | --- | --- | --- |
| 1주차 | 규칙 결정, 격자·입력·운반·undo, 기초 화면 | 순수 모델, 실행 가능한 한 방 | 성공·실패·되돌리기의 상태 일관성 |
| 2주차 | 함정·병사 복구, 입문 3방, 안내 | 세 방 플레이 흐름, 해결 테스트 | 세 방 처음부터 끝까지 완료 |
| 3주차 | 발판, 투입구, 벨트를 하나씩 구현 | 장치별 검사, 4~7단계 초안 | 충돌·점유·동시 처리·undo 통과 |
| 4주차 | 8단계 결합, 전체 진행, UI·아트·연출 | 8개 방 연결 빌드 | 모든 방 해결 가능, 상태 판독 가능 |
| 5주차 | 관찰 플레이테스트, 난이도 조정, 발표 준비 | 측정 기록, 수정 목록, 시연 경로 | 진행 차단 결함 해소, 분량 재산정 |
| 6주차 | 회귀 검사, 제출 환경 점검, 최종 발표 | 고정된 제출 버전과 안내 | 새 환경 실행, 자료·코드 버전 일치 |

이번 기초 작업은 1주차 기반과 2주차 핵심 규칙을 먼저 연결해 위험을 확인한다. 이것을 1·2주차의 모든 아트와 난이도 검증까지 완료한 것으로 표시하지 않는다.

### 11.1 다음 구현 순서

1. 세 방을 직접 플레이하여 조작 혼란과 반복 운반 구간을 찾는다.
2. 현재 칸 상호작용, 배치 후 회수 불가, 두 묶음 조립 규칙의 이해도를 확인한다.
3. 이 규칙을 유지할지 결정하고 입문방을 수정한다.
4. 구현한 4번 방에서 발판·문·재료 회수의 이해도를 관찰한다.
5. 구현한 5번 방에서 투입구·발판 연결과 출력 점유 안내를 관찰한다.
6. 6번 방에서 대기·벨트의 한 칸 이동과 물건 회수 시점의 이해도를 관찰한다.
7. 4~6단계에서 확인한 장치를 7단계에 결합하고 마지막에 8단계를 만든다.
8. 기본 규칙과 레벨이 안정된 뒤 최종 아트·사운드·연출을 적용한다.

### 11.2 기능별 커밋 기준

한 커밋은 설명할 수 있는 기능 또는 검증 단위를 담는다. 커밋 제목은 `docs`, `feat`, `test`, `fix` 등 목적을 드러내고 본문은 이유·행동 변화·검증을 기록한다.
계획과 코드가 달라지면 실제 구현에 맞게 계획 또는 코드를 수정한 뒤 다음 단계로 넘어간다. 예상 단위는 상세 설계, 데이터·모델, 복구 규칙, 화면·입력, 회귀 검사, 실행 안내다.
커밋을 잘게 나누기 위해 실행 불가능한 의존 순서를 만들지 않는다. 외부 푸시는 사용자가 요청한 기존 저장소와 브랜치로 진행하고 강제 푸시하지 않는다.

## 12. 분량, 플레이테스트, 위험 관리

### 12.1 원본 플레이 시간의 불일치

PPT의 전체 목표는 60~70분이다. 구간별 시간을 합하면 `3×(3~5) + 4×(10~15) + (20~30) = 69~105분`이다.
두 수치를 임의로 하나로 덮어쓰지 않는다. 프로토타입 세 방의 짧은 해결 시간은 최종 분량을 증명하지 않는다.
최초 플레이에서 읽기, 고민, 이동, 되돌리기, 재시작 시간을 따로 관찰한 뒤 전체 목표를 조정한다. 시간을 늘리려고 운반 거리를 늘리기보다 필요한 판단이 충분한지 먼저 검토한다.

### 12.2 관찰 기록 양식

| 항목 | 기록 내용 |
| --- | --- |
| 빌드·방 | 커밋 ID, 방 ID, 규칙 변경 여부 |
| 플레이어 조건 | 조작법을 미리 읽었는지, 퍼즐 경험 정도 |
| 시작·종료 | 첫 입력부터 완료까지, 중단 시 이유 |
| 첫 혼란 | 무엇을 해야 할지 몰랐던 위치와 문구 |
| 잘못된 예상 | 통행·조립·장치 결과를 오해한 순간 |
| 복구 행동 | undo·restart 횟수와 사용 이유 |
| 도움 | 힌트 없이 완료했는지, 제공한 힌트 내용 |
| 반복 작업 | 생각 없이 왕복한 구간과 체감 |
| 다음 수정 | 규칙·배치·안내 중 어느 부분을 바꿀지 |

처음에는 소수의 관찰 플레이로 큰 혼란을 찾는다. 사람 수가 적을 때 평균 시간만으로 난이도를 확정하지 않는다.
수정 후에는 같은 경험자의 단축 시간과 새 플레이어의 첫 시간을 구별한다.

### 12.3 주요 위험과 대응

| 위험 | 조기 징후 | 대응 |
| --- | --- | --- |
| 복구가 단순 배달로 느껴짐 | 순서를 바꿔도 결과가 같음 | 공유 통로·재료 사용 시점 검토 |
| 현재 칸 상호작용이 낯섦 | 앞 칸에서 반복 입력 | 발밑 강조와 현재 행동 안내 개선 |
| 2.5D가 좌표를 혼동시킴 | 원하는 칸과 다른 방향으로 이동 | 방향 안내와 바닥 윤곽 보강 |
| 병사 배치 규칙이 불공정함 | 회수할 수 있다고 예상 | 배치 전에 통행 차단·undo 안내 |
| 복구 후 자원 복제·유실 | 재시도 결과가 달라짐 | 전체 스냅숏과 자원 보존 검사 |
| 보조 장치 결합이 불안정함 | 처리 순서에 따라 결과가 바뀜 | 후보 수집과 동시 충돌 정책 고정 |
| 화면 자산 작업이 일정 지연 | 규칙 수정 때 아트도 재작업 | 임시 도형으로 레벨 먼저 검증 |
| 데이터 오류가 실행 중 드러남 | 방 전환에서만 예외 발생 | 시작 시 전체 방 검증 |
| 실행 위치에 따라 실패 | VS Code에서는 되고 다른 폴더에서는 실패 | 파일 기준 경로와 외부 폴더 실행 검사 |
| 테스트를 완성도로 오해 | 실제 조작·가독성 기록 없음 | 자동·창·관찰 검증을 분리 기록 |

### 12.4 후속 결정 목록

- 출구 빈손 조건이 의미 있는 판단을 만드는지, 불필요한 왕복만 만드는지 확인한다.
- 두 묶음 조립이 학습에 필요한지, 이후 방에서는 병사 조립 횟수를 늘릴지 결정한다.
- 배치 후 직접 회수 불가 규칙을 본편에서도 유지할지 결정한다.
- 레버 하나가 모든 함정을 가동하는 범위를 유지할지, 후속 방에서 그룹을 나눌지 결정한다.
- 발판의 허용 점유 대상과 문 닫힘 대기 표시가 실제 플레이에서 이해되는지 확인한다.
- 투입구 출력칸에 플레이어가 있을 때의 거절 규칙을 플레이로 확인한다.
- 벨트용 `B` 대기와 부품·병사만 내려놓는 안내가 실제 플레이에서 이해되는지 확인한다.
- 전체 60~70분 목표와 구간별 목표 중 무엇을 조정할지 측정 후 결정한다.
- 제출 환경의 Python 버전과 pico2d 설치 경로를 실제 실행으로 확인한다.

이 결정들은 후속 개발의 입력이다. 미정 항목을 구현 완료로 표시하지 않는다.
